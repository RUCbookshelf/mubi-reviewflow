# 2.1.6 团队流程接口与事务 Implementation Plan

> **For agentic workers:** 执行时使用已列出的 `subagent-driven-development` 技能逐包推进。此文件由 Sol 定稿；依赖、文件所有权、派单顺序以同目录 `2026-11-16-2.1.6-complete-dag.md` 为准。当前只完成规划，未派实施。

**Goal:** 固定逐条完成、来源发现、名册变更、真实保存和当前结果之间的接口，供 Terra 协调时直接引用。

**Architecture:** 完成事实优先，未完成部分按当前名单判断。任务锁与 collaboration.db 的 IMMEDIATE 事务串行化守协议操作；写请求仅提交一个实际业务目标，历史清空另遵专用多分区协议。

**Tech Stack:** Python 3.12.13 验证环境、stdlib sqlite3、现有 FastAPI/Pydantic、pytest/unittest、现有 Node 校验器；不加第三方依赖。

## C01　业务与适用模式

1. 完成键是 `(task_instance_id, stage, item_key)`，stage 仅 `stage1/stage2`。task_id 与独立 instance 不混用，不通过重新生成 instance 解锁已有任务。
2. 非空、明确应筛名单的全员 include/exclude，以及当时合法仲裁的 include/exclude，均是完成。空名单不自动满足；一个明确应筛人合法。
3. 完成时全 roster、required_uids、完整原始意见、来源、结论保留；成员/职责变化不重评已完成阶段，不补票、不重开、不强解锁。
4. stage1 exclude 短路；stage1 include 才判断 stage2；两个 include 才判断编码/评价资格。新成员可以直接参与尚未完成的 stage2。
5. 现行权限仍先查：属主只叠加管理权限，业务角色二选一且无旁路。完成优先不授予已移除者读写权。
6. 采用已核的 task_kind/team_latched/身份来源真值表，不由 server/desktop/AUTH_ENABLED 单独开关决定。独立、solo、手工分析、旧 CSV/CLI 原用途保留；无账号/无 grant 不自动判垃圾或注销。
7. 已封存完成不再检查旧票/proof 的当前适用性；raw 漂移仅作诊断。未封存的当前一致可以只读派生，但不能虚构过去完成时间。

1. opaque token 为服务端生成的 canonical JSON：version=1、base='task_dir'、relative（POSIX 相对路径）、source_user_id、source_library_id。拒绝绝对路径、drive、NUL、..、越界 symlink/junction、非 regular；最终核实际 library ID/UID/登记 generation/物理 claims。inode 是当次见证，不当永久逻辑 UUID。
2. 老 slug 只能来自可信任务/导入来源元数据或原登记，不能按当前 username 猜。不能解析的旧 token 是 issue；不把无账号/无 grant 的文件自动忽略或隔离。
3. **新建任务**：在尚未公开/授予业务访问的创建生命周期准备独立 owner/actor 库与 schema；collab 内注册唯一 instance、来源及 new_covered。复制旧任务/离线包/带历史库不能冒充全新无历史任务，进入 legacy 分支。
4. **存量任务**：利用已有 owner-only `/collaboration/repair` 的明确维护动作准备 schema/身份登记，再在受保护 collab 目标事务保存可核 adoption。纯 GET 和普通失败保存不 prepare/register/mark verified。repair 的多库 schema 准备是独立元数据阶段，可保留已准备 schema，不能描述成跨库原子或一次业务保存成功。
5. repair 即使角色未配置也能准备 pending 协议，让 owner 继续现有角色配置；必要库不可核则明确 pending/issue。配置入口与 repair 不受普通成员业务门锁死。不能在 GET 中自动补职责。
6. mark_legacy_verified_on 仅由上述显式 adoption 调用；精确低层 evidence 五字段沿现合同：sources、verification_scope、verification_method、conflict_handling、prior_history_unknown=True。evidence_ref 指向同 collab 事务的内部 receipt 证据；内含 task/owner/instance、源代次全集、实际枚举方法/范围、当前域 baseline、已知终局归档/观察、冲突结果、producer 协议版本、真实前向起点。
7. **legacy_verified 仅向前覆盖**，不恢复整个前史。pending/坏 coverage 不能用空表/None 当未完成。显式 adoption 证明“从此起点所有支持 producer/名册边界受控”，记录当时可证明的当前完成；之后的负发现仅证明该覆盖期内无持久完成，不声称旧史从未完成。首次受保护观察前 CLI 已覆盖丢失的前史仍 unknown，不能伪恢复。
8. 单键可信当前一致可在 pending 下形成观察候选；相关当前意见及该键可能 holder 必须已核，不能让未知 holder 掩盖可能相反的旧完成。局部可证不要求无关键/库全体升级，且不自动升级任务覆盖。旧史未知与**当前发现来源未决**分别呈现；后者始终阻塞相关键，不能通过重命名 verified 消除。
9. 所有可能持有 actor 观察的来源都登记，包含不在某阶段 required 的合法 observer。来源退休/重入使用新 registration/generation，不继承 watermark。
10. 正常业务请求不补登记；必要 source 未登记时 typed 阻塞。邀请/显式 owner repair 可先做其本来授权的账号/库准备；身份准备与角色提交不是跨库原子，失败报告实际已准备账号/库，不能宣称账号创建已回滚。
11. 任务创建、邀请/角色入口、repair、task-package 恢复/导入为所有生命周期 hook；恢复不能默默换 UUID/instance。已有协议却丢失 registry 的任务不自动当全新 legacy；显式来源未决/恢复正确元数据。

退休源无需再次打开的唯一优化：管理 producer 在连续 collab 屏障和保留源事务中完整 list/验证本 instance 的全部 actor seals，归档到 collab，并记录完整枚举证明与每条 ID/hash/原时间在内部 receipt；同 commit retire/revision。opaque watermark 只指向该证据。读取者核证据版本、task/UID/library/registration/generation、退休绑定、collab 中逐条副本和全部枚举流程来源，才可判该退休代次无后续协议 seal。数量相等、hash、retired 或 watermark 单独均不足；证据缺失仍作为可能 holder。

## C10　名册管理与逐条仲裁

管理：所有五入口共一个 collab 目标协调器；调用前现读 owner/目标成员合法性，已成功 receipt 直接返。保旧集 → 归档已知 actor seals/receipts → 定向枚举旧 required 票键并集，按初筛到复筛计算旧集观察 → 归档/观察 → 四 borrowed writer → 实际有 roster/source 变化才推进 revision → 新集首次一致 → receipt → 一次 collab commit。切断的来源无法确认时整个角色变更回滚；幂等 revoked:false 不新增无条件文件动作。账号/空库准备与已提交后的旧可选文件归档另外记真实结果，不能先搬库断发现。
